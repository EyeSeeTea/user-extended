## Context

See proposal.md (Why). Current state that shapes the approach:

- `UserBulkEditPage` keeps the rows in a `users` state that is also the `initialValues` of react-final-form. `addRow` changes that state, so the form reinitializes and drops unsaved edits; `removeRow` changes only the form (`form.change`), so the state still has the deleted row and the next reinitialization brings it back.
- The page reads `location.state as { users }`; with no state (`null`) the destructuring throws before the existing `users.length === 0 → <Navigate to="/">` guard runs.
- New rows and `/new` start from `defaultUserProps`, which has `id: ""` and one empty-id item in `userRoles`, `userGroups`, `organisationUnits`, `dataViewOrganisationUnits` and `searchOrganisationsUnits`. `defaultUserProps` is also used by import (`ImportUsersUseCase`), so it stays as it is.
- `SaveUsersUseCase` validates every user with `User.createExisted`. `User` already has the new-user rules (`createNew`, `isExistingUser: false`) and owns the generation of new identifiers, so UI drafts must remain id-less until save.
- `UserD2ApiRepository.save()` prefetches the users by id and merges each one with its existing record if there is one (`buildUserToSave(undefined, user)` for new users). Import and replicate already create users through it, so it handles new users once ids are valid.
- Username is rendered `disabled={isEdit}`, and bulk edit passes `isEdit: true` for every row.

## Goals / Non-Goals

**Goals:**
- One save path for existing and new users (bulk edit and `/new`), with the new-user rules applied in the domain before any request.
- Validation errors shown in the form, not only as a snackbar.

**Non-Goals:**
- Changing `defaultUserProps` or how import creates users.
- Per-field inline errors in the grid: errors are listed in the form's error box, by user and field.
- Changing `UserD2ApiRepository.save()` or `TransferFF`.

## Decisions

### Data flow

```
UserBulkEditPage (renders) → useUserBulkEdit (presentation logic, webapp)
UserEditPage (webapp)
  ├─ new row / new user ← newUserProps()            (domain/entities/UserProps.ts)
  └─ save / onSubmit → compositionRoot.users.save(users)
        SaveUsersUseCase (domain/usecases)
          ├─ row with id → User.createExisted(props)
          ├─ id-less row → User.createNew(props)      (generates id)
          ├─ any error → Future.error(message by user and field), nothing sent
          └─ userRepository.save(users)               (data, unchanged)
  ← error → shown as the form's submit error
```

### 1. Rows live only in the form
The page keeps its initial users as fixed `initialValues` (from the navigation state, never updated afterwards). "Add user" (`addUser` in the hook, §8) appends the new row with the form API (`form.change("users", [...current, newUser])`), as `removeRow` already does. The form is the only source of truth for rows, so it never reinitializes.
- *Alternative:* keep the `users` state and sync it on every change (`FormSpy`), or set `keepDirtyOnReinitialize`. Rejected: two sources of truth for the same rows, and `keepDirtyOnReinitialize` would still bring back deleted rows.

### 2. Missing navigation state
Read the state as optional (`location.state?.users ?? []`) so the existing empty-users guard redirects to `/`.

### 3. New-user template
A `newUserProps()` function in `UserProps.ts` returns an id-less `NewUserProps` draft based on `defaultUserProps`, with empty collections (`userRoles`, `userGroups`, `organisationUnits`, `dataViewOrganisationUnits`, `searchOrganisationsUnits`, `authorities`), no audit references and an empty password. It is a function so every call gets fresh dates. Bulk edit "Add user" and `/new` use it; the hardcoded password goes away. The draft becomes a domain `User`, with an id generated by `User.createNew`, only when it is saved.
- *Alternative:* fix `defaultUserProps`. Rejected by the task: import depends on it.

### 4. Telling new drafts from existing users in the use case
`SaveUsersUseCase` accepts `UserToSave`, a union of existing `UserProps` (required id) and `NewUserProps` (no id). Rows with an id are validated with `createExisted`; id-less drafts are validated with `createNew`, which generates the id. This keeps identity creation inside the domain and leaves import and replication unchanged.
- *Alternative:* ask the repository which ids exist. Rejected: it adds a request, weakens `User.createNew` by requiring it to preserve externally supplied identifiers, and changes callers that previously relied on it always generating a new id.

### 5. Errors reach the form
The use case joins the validation errors into one message that names each invalid user (username or name, or its row) and its fields, using the existing `ValidationError` helpers. The bulk edit `save` (in the hook, §8) returns it as `{ [FORM_ERROR]: message }` so the form's existing `NoticeBox` shows it (today it returns the bare string, which react-final-form ignores, and only the snackbar shows it). `UserEditWizard` already shows the string returned by `onSave` as its submit error.

### 6. Editable fields per row
Bulk edit passes `isEdit` per row: `false` for id-less rows added in the page, `true` for users that came from the list. When a row is added, `username` and `password` are added to the visible columns if they are missing.

### 7. `/new`
`UserEditPage` uses `newUserProps()` instead of `{ ...defaultUserProps, id: generateUid() }`, and `UserListTable` re-enables `onActionButtonClick: () => navigate("/new")` (removing the FIXME).


### 8. Presentation logic in a hook
`useUserBulkEdit`, next to the page, holds the page's presentation logic: the users read from the navigation state and the redirect decision, the final-form instance (`createForm`, fixed initial values), `addUser`, `removeUser(row)`, the visible columns and the column selector, the import summary and `save` (use case, loading, snackbar, summary, back to the list). `UserBulkEditPage` renders `<Form form={form}>` with what the hook returns, and the grid rows get `removeUser` through `itemData` instead of `useForm`. Fields and their validation stay as they are: react-final-form field components shared with `/new` and the import table.
- *Alternative:* a hook independent of the form (rows as React state, controlled fields, validation from the domain). Postponed: the FF fields are shared with the wizard and the import table, and the domain lacks rules the UI validators have (phone, WhatsApp, email of existing users). Logged in `docs/technical-debt.md`.

## Risks / Trade-offs

- [The wizard behind `/new` may have other problems not covered by the task, since it has been disabled since 2023] → test `/new` end to end on DHIS2 2.42 during the change; anything outside the save path goes to a separate task.
- [`updateUserGroups` after the metadata post may not handle users that did not exist before] → covered by the end-to-end check; import already creates users through the same `save()`.
- [Errors are listed in one box, not next to each cell] → acceptable for this task (non-goal); a grid of 6+ columns per user still says which user and field.
- [`TransferFF` treats an empty-id ref as selected] → no longer reachable from bulk edit or `/new`; import still uses `defaultUserProps`, but it does not render the form.

## Migration Plan

No data or API migration. Rollback is reverting the change's commits.
